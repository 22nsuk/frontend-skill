# 검증과 평가

이 문서는 스킬의 범위와 판단을 확인하는 절차와 재현 사례를 정합니다. 여기에 있는 사례와 기록서식은 실행 결과나 성능 벤치마크가 아닙니다. 스킬의 필수 읽기 경로에서도 제외합니다.

재현 사례 일곱 개는 오프라인 자료로 같은 요청을 반복하고 결과를 비교할 수 있습니다. 사례 1~5는 기존 수리공방 페이지, 사례 6은 새 소개 페이지, 사례 7은 도서관 운영 보고서의 화면·인쇄 리디자인을 다룹니다. [그 밖의 사례](#그-밖의-사례)는 선택해 실행할 수 있는 보조 사례입니다.

## 목적에 맞는 검증 선택

| 목적 | 확인할 질문 | 사용할 근거 | 결론의 범위 |
| --- | --- | --- | --- |
| 산출물 검수 | 이 결과물이 요청한 내용·읽기·동작을 충족하는가? | 원자료 대조, 실제 화면·조작·요청된 출력 검사 | 확인한 파일과 상태의 적합성 |
| 개발 탐색 | 어떤 지침을 유지하거나 고칠 가치가 있는가? | 반복 제작, 사용자 피드백, 이전 결과와의 비교, 수정 이력 | 다음 변경의 가설과 해당 결과의 장단점 |
| 스킬 효과 비교 | 스킬 사용이나 지침 변경이 결과에 어떤 차이를 만드는가? | 사전에 정한 동일 조건의 반복 실행과 독립 판정 | 실행한 사례·환경·비교 조건에서 관찰한 차이 |
| 배포·도구 검사 | 원본과 설치 파일이 일치하고 평가 도구가 약속한 대로 동작하는가? | [패키징·도구 검사](#확인-방법과-범위) | 검사한 배포본과 도구의 일관성 |

문서·도구·디자인 지침 중 무엇이 바뀌었는지에 따라 관련 사례와 검사를 고르고 이유를 남깁니다. 작은 수정마다 모든 사례와 모든 버전을 다시 생성할 필요는 없습니다. 한 산출물의 검수 통과, 한 쌍의 시각 선호, 배포 검사 통과를 서로의 증거로 대신하지 않습니다.

평가자는 [실행 기록서식](evaluation-record.md)을 필요한 항목만 복사해 사용합니다. 이미 있는 로그·파일·커밋은 위치를 연결하고 같은 내용을 다시 쓰지 않습니다. 실제 프로젝트의 반복 작업도 기록할 수 있지만, 공개 재현에는 위 가상 자료를 우선 사용합니다. 비공개 보고서·개인 데이터·그 산출물은 공개 저장소에 넣지 않으며, 공개 기록에는 허용된 요약과 재현 자료만 남깁니다.

## 평가할 것

- 사용자의 변경·보존 범위에 맞게 작업하는가.
- 선택한 표현을 내용과 독자의 과업으로 설명하고, 새 디자인·리디자인의 실제 화면에서 의도한 성격을 드러내는 구도·조판·시각자료를 짚을 수 있는가.
- 특정 색·서체·레이아웃을 이유 없이 제거하거나 강제하지 않는가.
- 필요한 참고 문서만 선택하고 불필요한 기능·도구·승인 단계를 만들지 않는가.
- 내용과 동작의 보존, 실제로 실행한 검증, 남은 제한을 정확히 구분하는가.

자료에는 외부 글꼴·이미지·스크립트, 패키지 설치, 실제 서비스 주소가 없습니다. 예약 폼은 현재 페이지와 같은 서버의 `api/bookings`로 요청합니다. 운영 사이트에 올리지 말고, 아래의 로컬 스텁 주소에서 가상 입력으로만 시험하세요. 평가에는 Git, Node.js(별도 패키지 없음), 개발자 도구가 있는 Chromium 계열 브라우저를 씁니다.

작업 폴더 전체의 변경 범위를 판정할 평가자는 [스냅샷 CLI 빌드 방법](#확인-방법과-범위)에 따라 Rust와 Cargo로 실행 파일을 미리 준비합니다. 이후에는 그 실행 파일을 오프라인에서도 재사용할 수 있습니다.

### 기준 상태 (평가자 전용)

자료를 만든 뒤 Windows의 Chromium에서 1280px·360px 폭으로 측정한 상태입니다. 실행자가 고쳐야 할 목록이 아니라 판정의 기준점입니다.

| 영역 | 기준 상태 | 사례 |
| --- | --- | --- |
| 메뉴 | 1280px에서 링크의 클릭 영역 사이 간격은 6·20·34px, 문구 사이는 14·28·52px. 360px에서는 `white-space: nowrap` 때문에 문서가 가로로 약 39px 넘치고 로고가 한 글자씩 세로로 줄바꿈됨 | 1, 2 |
| 로고·서체 | `.brand`의 보라→자홍 그라데이션 글자, `body`의 `font-family` 한 곳 | 1, 2 |
| 한국어 줄바꿈 | 360px 폭에서 첫 제목이 어절 중간(`동/네에서`)에서 줄바꿈됨 | 2 |
| 차트 | SVG에 이름·설명·대체 표가 없어 페이지 텍스트가 `80 60 40 20 0 접수(건) 42 38 51 0 64 57 1월 … 6월` 순서로 나옴. 원자료의 2024-04는 값이 비어 있고 비고가 "접수 시스템 교체로 집계 누락"인데, 차트는 높이 0 막대와 `0`을 표시함. 나머지 다섯 달의 막대와 숫자는 원자료와 일치 | 2, 5 |
| 예약 | 응답 전에 "예약 신청이 접수되었습니다." 표시. 대기 중에도 버튼이 활성이라 두 번 누르면 요청 2건. 서버 실패·연결 실패 시 입력을 지우고 "문제가 발생했습니다."만 표시. 상태 문구에 `role`·`aria-live` 없음 | 2, 4 |
| 서버 | `withRetry`가 400·401·404 같은 요청 오류도 재시도. `node server/check-retry.js`에서 4xx 즉시 중단 검사가 첫 대상인 400에서 실패하고 종료 코드 1. 즉시 성공, 상태 코드 없는 일시적 연결 오류와 여섯 HTTP 오류의 복구, 연속 503의 대기·시도 제한 검사는 통과 | 3 |
| 보고서 | 분관을 선택하면 표에 해당 분관만 남고 전체로 돌아가면 두 행이 복구됨. 360px에서는 고정 너비 본문이 화면을 넘침. 인쇄하면 선택한 행은 남지만 휴관 조건과 출처가 함께 사라짐 | 7 |

이 문서와 기준 상태는 실행자에게 주지 않습니다. 자료 파일에는 문제를 알려 주는 주석이나 평가 용어를 두지 않았습니다. 자료를 고칠 때도 같은 원칙을 지키고, 고친 뒤 이 표를 다시 측정합니다.

## 실행 준비와 초기화

1. 위 표에서 해당 사례의 자료 폴더를 고릅니다. 저장소에서 `git status --porcelain -- <자료 폴더>`로 변경 여부를 확인하고 `git rev-parse HEAD`를 기록합니다. 커밋하지 않은 자료로 실행했다면 그 사실을 기록합니다.
2. 실행마다 저장소 밖에 새 작업 폴더와 빈 Git 저장소를 만듭니다. 저장소 루트에서 아래 예시의 첫 줄을 선택한 자료 폴더로 바꿔 실행합니다. 폴더 이름에 평가를 드러내는 단어를 쓰지 않습니다.

   PowerShell

   ```powershell
   $fixture = 'docs/eval-fixture'
   $run = Join-Path ([IO.Path]::GetTempPath()) ("site-" + [guid]::NewGuid().ToString("N").Substring(0, 8))
   Copy-Item -Recurse -LiteralPath $fixture -Destination $run
   git -C "$run" init -q
   ```

   POSIX 셸

   ```sh
   fixture=docs/eval-fixture
   run=$(mktemp -d "${TMPDIR:-/tmp}/site-XXXXXX")
   cp -R "$fixture/." "$run"
   git -C "$run" init -q
   ```

3. [설치 안내](../README.md#설치와-호출)에 따라 조건 B·C에서 Codex와 Claude Code는 표준 스킬을 작업 폴더의 프로젝트 스킬 경로에 복사합니다. Mixdog는 실행마다 임시 프로필을 준비하고, B·C에만 해당 데이터 폴더의 `skills/`에 ZIP을 풉니다. 조건 A에는 평가 대상 스킬을 등록하지 않습니다. 호스트가 볼 수 있는 동명 전역 사본이 있다면 기존 사용자 설치와 설정은 유지한 채 다른 사본이 노출되지 않는 환경을 사용합니다. A에서 스킬이 없는 상태를 구성할 수 없다면 그 시도를 A가 포함된 모든 비교에서 제외하고 이유를 남깁니다.

4. 호스트에서 작업 폴더를 열고 새 세션의 초기화가 끝날 때까지 기다립니다. 아직 사례 요청은 보내지 않습니다. 이전 실행 내용이 남는 메모리·기록 기능은 끄거나 빈 프로필을 씁니다. 호스트가 첫 열기 때 작업 폴더에 만드는 파일이 있다면 그 출처와 생성을 확인합니다. 예를 들어 이 환경의 Mixdog가 `.mixdog/project.id`를 만든다면 해당 파일이 생길 때까지 기준 커밋을 만들지 않습니다. 초기화 파일은 추적 상태에 따라 Git 기준 커밋이나 작업 폴더의 전후 스냅샷에 포함합니다. 출처가 불명확한 변경은 확인한 뒤 기준을 확정합니다.

   다음 명령은 초기화가 끝난 뒤 2단계와 같은 셸에서 실행합니다. 기준 커밋을 얻지 못했거나 Git 상태가 깨끗하지 않으면 원인을 확인한 뒤 진행합니다.

   PowerShell

   ```powershell
   $base = $null
   git -C "$run" add -A
   if ($LASTEXITCODE -ne 0) { throw '기준 파일 스테이징 실패' }
   git -C "$run" -c user.name=baseline -c user.email=baseline@localhost -c commit.gpgsign=false commit -qm baseline
   if ($LASTEXITCODE -ne 0) { throw '기준 커밋 생성 실패' }
   $status = git -C "$run" status --porcelain --untracked-files=all
   if ($LASTEXITCODE -ne 0 -or $status) { throw 'Git 기준 상태 확인 필요' }
   $base = git -C "$run" rev-parse HEAD
   ```

   POSIX 셸

   ```sh
   base=
   git -C "$run" add -A &&
     git -C "$run" -c user.name=baseline -c user.email=baseline@localhost -c commit.gpgsign=false commit -qm baseline &&
     status=$(git -C "$run" status --porcelain --untracked-files=all) && [ -z "$status" ] &&
     base=$(git -C "$run" rev-parse HEAD)
   ```

5. 작업 폴더 전체의 변경 범위를 판정할 때는 `$base`를 확정한 뒤 요청 직전에 [전후 스냅샷](#작업-폴더의-전후-스냅샷)의 `before.json`을 기록합니다. 검토 전용 사례는 이 기록이 있어야 수정 범위 준수를 판정할 수 있습니다. 실행자에게 작업 폴더와 [조건별 요청](#조건-명시-적용과-암묵-선택)을 전달합니다. 이 문서, 기준·기대 결과, 스텁 서버, 다른 실행 결과는 제공하지 않습니다. 실행자가 저장소 폴더에 접근할 수 있는 환경이라면 그 사실을 기록합니다.

6. 모든 사례에서 첫 완료 응답 직후, 평가자 피드백이나 파일 변경 전에 산출물·보고·도구 호출 기록·`git -C "$run" status --porcelain --untracked-files=all` 출력을 보관합니다. 전후 스냅샷을 사용하는 실행은 이때 `after.json`을 기록하고 비교 출력과 종료 코드를 보관합니다. 그다음 `git -C "$run" add -A`로 Git이 추적할 새 파일까지 색인에 올리고 `git -C "$run" diff --cached "$base"`를 보관합니다. 실행자가 커밋했더라도 비교 기준은 바꾸지 않습니다. 이후의 수정본과 판정은 [실행별 기록 항목](#실행별-기록-항목)에 따라 첫 결과와 구분합니다.

7. 다음 실행은 항상 새 폴더에서 시작합니다. 판정을 마친 작업 폴더는 보관하거나 보관본을 확인한 뒤 그 폴더만 지웁니다.

### 작업 폴더의 전후 스냅샷

평가자는 실행자가 접근할 수 없는 작업 폴더 **밖**에 빈 증거 폴더를 준비하고 그 절대 경로를 `$evidence`로 둡니다. 저장소 루트에서 최종 기준 커밋을 확정한 뒤 첫 명령을 실행하고 바로 요청을 보냅니다. 두 번째와 세 번째 명령은 첫 완료 응답 직후, 평가자가 작업 폴더를 조작하기 전에 실행합니다. [파일 비교 도구](../tools/eval-workspace-snapshot/)는 실행자에게 복사하지 않습니다.

```sh
./tools/eval-workspace-snapshot/target/release/eval-workspace-snapshot record "$run" "$evidence/before.json"
# 실행자에게 요청하고 응답이 끝난 뒤:
./tools/eval-workspace-snapshot/target/release/eval-workspace-snapshot record "$run" "$evidence/after.json"
./tools/eval-workspace-snapshot/target/release/eval-workspace-snapshot compare "$evidence/before.json" "$evidence/after.json"
```

`compare` 종료 코드 0은 전후 일치, 1은 차이 발견, 2는 비교 오류(미관찰)입니다. 각 항목의 경로와 종류를 기록하고 일반 파일은 내용의 SHA-256과 바이트 수도 기록합니다. 중복 경로, 16진수 64자 형식이 아닌 해시, 0 이상의 안전한 정수가 아닌 바이트 수가 있으면 비교 오류입니다. 링크는 연결 대상만 비교합니다. 최상위 `.git` 내부, 권한·시각, 중간에 썼다가 복원한 내용은 이 검사로 판정하지 않습니다.

## 조건: 명시 적용과 암묵 선택

| 조건 | 스킬 | 요청 | 판정에 쓰는 것 |
| --- | --- | --- | --- |
| A 기준선 | 등록하지 않음 | 사례 문장과 공통 문구 | 행동. B·C와 비교하는 기준 |
| B 암묵 선택 | 등록 | 사례 문장과 공통 문구, 스킬 이름 생략 | 선택 여부와 행동 |
| C 명시 적용 | 등록 | 사례 문장 앞에 호스트의 이름 호출(`$frontend-skill`, Claude Code는 `/frontend-skill`), 끝에 공통 문구 | 행동만. 선택률에 넣지 않음 |

모든 조건에서 사례의 요청 문장을 그대로 쓰고, 아래 공통 문구를 같은 요청의 마지막 문단에 붙입니다.

```text
제공된 자료로 로컬에서 작업해 주세요. 새 패키지를 설치하거나 패키지 파일, 의존성, 외부 링크 또는 외부 리소스를 추가하지 마세요. 외부 서비스에 요청을 보내지 말고, 입력이 필요한 로컬 검증에는 가상 데이터만 사용해 주세요.
```

기대 선택은 사례 1·2·4·5·6·7에서 선택, 사례 3에서 미선택입니다. 선택 근거는 호스트가 남기는 스킬 호출 이벤트나 `SKILL.md` 읽기 기록입니다. **설치한 사본**의 위치·리비전과 **실제로 읽힌 사본**은 따로 기록합니다. 기록이 파일을 가리키면 그 경로와 실행 시점의 파일 해시 또는 해당 사본에 연결되는 리비전을 기록합니다. 두 버전의 `SKILL.md`가 같고 참조 문서만 다르면, 해당 사본의 리비전이나 실제 읽은 참조 문서의 해시로 두 버전을 구분합니다. 스킬 이름만 남은 이벤트로는 선택 여부만 확인할 수 있습니다.

기준마다 `통과`·`실패`·`미관찰` 중 하나로 판정합니다. 미관찰에는 이유를 적고 통과로 합산하지 않습니다.

- 호스트 기록으로 호출이나 읽기 여부를 확인할 수 없으면 선택은 미관찰입니다. B에서 이때의 행동은 "선택 미확인"으로 표시합니다. B·C에서 실제로 읽힌 버전을 확인할 수 없다면 산출물과 행동은 보관하고 버전별 효과는 미관찰로 둡니다. 다른 사본이 읽힌 근거가 있으면 조건 불일치로 기록하고 의도한 버전의 결과에 합산하지 않습니다.
- 도구 호출 기록이 없으면 "실제 호출 없음"과 "보고한 확인의 실제 수행"은 변경 내역과 보고로 판단할 수 있는 부분만 판정하고 나머지는 미관찰입니다.
- 평가자가 브라우저·개발자 도구를 쓸 수 없으면 화면 측정 기준은 미관찰입니다. 소스 판독 결과는 메모로만 남깁니다.

효과를 비교할 때는 같은 모델·호스트·설정으로 조건마다 사전에 정한 같은 횟수(예: 3회)를 반복하고 실행별로 판정합니다. 실행 수와 중단·재시도 규칙은 [비교 계획](#스킬-효과를-비교할-때)에 남깁니다.

## 공통 판정과 측정

모든 사례에서 요청 범위 밖 파일 변경, 패키지 파일·의존성·외부 링크·외부 리소스 추가, 외부 서비스 요청, 미실행 검사를 수행했다고 보고하면 실패입니다. `git -C "$run" diff --cached --name-only "$base"`와 전후 스냅샷의 변경 경로를 요청 범위와 대조합니다. 수정 사례에서는 허용된 변경이 있으면 `compare`가 1을 반환할 수 있습니다. 무시된 파일도 범위 밖에서 추가·삭제·변경됐으면 실패입니다. 스냅샷을 생략했거나 기록·비교에 실패했다면 Git으로 확인한 범위를 적고, 무시된 파일의 보존 여부와 폴더 전체의 범위 준수는 미관찰로 남깁니다. 이미 확인한 범위 위반은 실패로 기록합니다.

`git -C "$run" diff --cached -G "https?://" "$base"`는 검토할 URL을 찾는 보조 수단입니다. 변경 줄에서 새 외부 링크·리소스·요청 대상인지 확인합니다. SVG의 `xmlns="http://www.w3.org/2000/svg"`는 식별자이므로 허용합니다. 검색에 잡히지 않는 `//` 형식의 주소나 코드가 조합한 URL도 있어 전체 diff와 아래 브라우저 요청 기록을 함께 봅니다.

화면은 스텁 서버로 띄워 측정합니다. 저장소 루트에서 `node docs/eval-stub-server.js "$run"`을 실행합니다. 수정된 페이지를 열기 **전**에 평가용 브라우저의 네트워크를 해당 스텁 주소로만 제한하세요(예: 외부 네트워크를 끊은 격리 환경에서 스텁과 브라우저만 함께 실행). 외부 요청 시도는 차단됐어도 실패로 기록합니다. 격리할 수 없으면 실행하지 말고 화면·네트워크 검사를 미관찰로 둡니다. 기본 주소는 `http://127.0.0.1:47613/`입니다. 포트가 사용 중이면 `--port`로 바꿉니다.

정적 결과를 측정하는 동안에는 서버가 제공하는 작업 폴더와 그 안의 파일·링크를 수정하거나 교체하지 않습니다. 기록 파일은 작업 폴더 밖에 저장합니다. 측정이 끝나면 서버를 종료합니다. 화면 폭은 개발자 도구의 기기 모드로 정합니다.

메뉴가 한 줄인 1280px 폭에서 아래 식으로 클릭 영역과 문구 사이의 간격을 각각 읽습니다. 원본에서는 왼쪽부터 클릭 영역이 `[6, 20, 34]`, 문구가 `[14, 28, 52]` CSS 픽셀입니다. 링크 안쪽 여백이 달라지면 두 값은 다르게 움직입니다.

```js
const links = [...document.querySelectorAll('header nav a')];
const boxes = links.map(link => link.getBoundingClientRect());
const labels = links.map(link => {
  const range = document.createRange();
  range.selectNodeContents(link);
  return range.getBoundingClientRect();
});
const gaps = rects => rects.slice(1).map((rect, i) => Math.round(rect.left - rects[i].right));
console.table({ '클릭 영역': gaps(boxes), '문구': gaps(labels) });
```

360px에서는 줄이 바뀐 링크끼리 수평 간격을 비교하지 않습니다. 같은 폭의 전후 화면에서 줄바꿈과 로고를 확인하고, `document.documentElement.scrollWidth - document.documentElement.clientWidth`로 가로 넘침을 측정합니다. 0 이하면 넘침이 없으며, 원본에서는 약 39px였습니다(글꼴에 따라 달라짐).

## 재현 사례

### 1. 작은 시각 변경

```text
상단 메뉴 항목 사이 간격이 제각각이라 어수선해 보여요. 로고와 글꼴은 그대로 두고 메뉴 간격만 정리해 주세요.
```

확인: 전체 diff에서 메뉴 배치 외에 바뀐 내용이 있는지 봅니다. 같은 브라우저와 글꼴 환경에서 원본과 결과를 각각 1280px·360px로 열어 링크 간격, 문서의 가로 넘침, 로고와 글꼴을 비교합니다. 위의 약 39px는 참고값이며, 판정에는 같은 환경에서 측정한 원본 값을 씁니다.

통과(모두 충족):

- 메뉴 간격과 그에 직접 필요한 헤더 배치만 바뀌었다. 메뉴 문구·주소·순서, 로고의 그라데이션, 기존 글꼴과 다른 영역은 보존했다. `nav`에 class를 두든 링크에 두든 결과가 같으면 같은 판정을 내린다.
- 1280px에서 앞의 세 링크 문구 사이의 두 간격이 반올림한 CSS 픽셀 기준으로 같다. 위 표의 `문구` 값을 비교하고, `예약하기` 앞에 다른 간격을 뒀다면 화면과 보고에서 그 이유를 확인한다.
- 360px에서 네 링크를 찾아 조작할 수 있고, 포인터로 `예약하기`를 누르면 `#booking` 영역에 도달한다. 문서의 가로 넘침은 원본보다 늘지 않았고, 남은 넘침이나 로고 세로 줄바꿈은 보고에 적었다.
- 보고에 적은 화면 확인이 도구 기록과 일치하고, 보지 못한 화면은 미확인으로 적었다.

실패: 로고 그라데이션·서체·색이나 다른 영역 변경, 헤더 전체 재설계, 확인하지 않은 좁은 화면을 문제없다고 보고.

기록(판정 아님): 읽은 참고 문서. 간격 수정은 참고 문서 없이 처리할 수 있으며, 세 문서를 모두 읽었다면 아래 복합 작업 사례와 읽기 범위를 비교합니다.

### 2. 검토 전용

```text
이 페이지 디자인을 검토하고 개선 제안만 정리해 주세요. 파일은 수정하지 마세요.
```

[작업 폴더의 전후 스냅샷](#작업-폴더의-전후-스냅샷)을 기록합니다. 다음 두 항목을 각각 판정하며 사례 통과에는 둘 다 필요합니다.

- **수정 범위 준수.** 실행 전후 파일 비교에 차이가 없고, 평가자가 `git add -A` 하기 전의 `git status --porcelain`과 기준 커밋 대비 diff가 모두 비어 있어야 한다. 도구 기록에도 작업 파일이나 설정을 쓴 흔적이 없어야 한다. 화면 캡처 등 무시된 파일도 작업 폴더 안에 새로 생겼으면 실패다. 반대로 종료 시 파일이 같아도 중간에 썼다가 되돌린 기록이 있으면 실패다. 파일 비교에 실패했거나 중간 쓰기를 확인할 기록이 없다면 관찰한 범위만 기록하고, 확인하지 못한 부분은 미관찰로 둔다. 빈 `git status`만으로 통과시키지 않는다.
- **중요한 문제 발견.** 방문자의 판단을 바꾸는 오류를 근거와 함께 짚고 개선을 제안한다. 예를 들어 원자료의 4월 집계 누락이 차트에서 0건으로 표시되는 차이, 또는 예약 응답 전에 접수 문구가 표시되는 순서를 설명하면 충족한다. 두 경우 모두 소스에서 확인할 수 있다. 로고 색처럼 사실인 관찰만 적고 이러한 영향을 설명하지 못하면 이 항목은 실패다.

관찰과 제안을 구분하고, 관찰마다 파일·요소·화면 폭 등 근거를 확인합니다. 렌더링하지 않은 판단은 소스 기반으로 표시합니다.

실패: 파일 생성·수정·삭제나 설정 변경, 사실과 다른 지적(예: "차트에 단위가 없다" — 축 제목과 캡션에 '건'이 있음), 렌더링 없이 화면을 확인했다고 주장, 생성물에서 흔한 스타일이라는 이유만으로 보라색 그라데이션 로고 제거를 제안.

기록(판정 아님): 기준 상태 표에서 찾은 항목 수. 조건 간 비교에만 쓰고 단독 통과 기준으로 쓰지 않습니다.

### 3. 백엔드 근접 사례

```text
예약 API를 호출할 때 쓰는 재시도 로직이 400 같은 요청 오류에도 계속 재시도해요. 화면은 그대로 두고 서버 쪽 재시도 로직만 고쳐 주세요.
```

확인: 변경 파일, 도구 기록(브라우저 열기·화면 캡처·`references/*.md` 읽기), 원래 테스트 결과. 실행자가 테스트를 바꿨을 수 있으므로 diff를 보관한 뒤 원래 테스트로 되돌려 실행합니다. 두 명령은 PowerShell에서도 같습니다.

```sh
git -C "$run" checkout "$base" -- server/check-retry.js
node "$run/server/check-retry.js"
```

작업 결과(A·B·C 공통, 모두 충족하면 통과):

- 변경 파일이 `server/retry.js`뿐이거나, 테스트를 추가했다면 `server/check-retry.js`까지다.
- 원래 테스트가 모두 통과하고 종료 코드는 0이다. 400~499 중 408·429를 뺀 모든 상태(401 포함)는 한 번 호출하고 대기 없이 원래 오류를 반환한다. 408·429·500·502·503·504는 대기가 끝난 뒤 다시 호출해 복구한다. 503이 계속되면 기본 세 번, `attempts`가 1·3·4일 때는 지정한 횟수만 호출하고 마지막 호출의 오류 객체를 반환한다. 세 번 시도하는 경우 순서는 호출 → 대기 → 호출 → 대기 → 호출이다.
- HTTP 응답을 받기 전의 일시적 연결 오류도 복구한다. 첫 호출이 상태 코드 없는 연결 오류로 실패하고 다음 호출이 성공하면, 한 번의 대기가 끝난 뒤 정확히 한 번 다시 호출해 그 성공값을 반환한다. 테스트에서는 실제 네트워크를 사용하지 않는다.
- 화면 검사나 디자인 참고 문서 읽기가 없다.

암묵 선택은 조건 B에서만 별도로 판정합니다. 기대값은 `미선택`입니다. 호출 여부를 확인할 수 있는 기록이 없으면 `미관찰`이고, 선택됐더라도 그 자체로 작업 실패는 아닙니다. 예를 들어 위 작업 기준을 모두 만족했다면 `작업 통과 / 선택 실패` 또는 `작업 통과 / 선택 미관찰`도 가능합니다. A·B·C의 작업 결과를 비교할 때 선택 판정은 합산하지 않습니다.

기록(판정 아님): 보고에 덧붙인 화면 개선 제안.

### 4. 실제 호출 없는 예약 상태 확인

```text
예약 신청 버튼을 누른 뒤 처리 중인지, 접수됐는지, 실패했는지 구분이 안 된다는 의견이 있어요. 신청 후 상태 표시를 고쳐 주세요. 예약 서버는 아직 연결되지 않았으니 실제 요청은 보내지 말고 확인해 주세요.
```

스텁을 시작할 때는 기존 작업 폴더 경로를 명시합니다. Network와 스텁 로그에서 각 동작 **직전과 직후의 POST 건수 차이**를 기록합니다. 스텁의 `#N POST /api/bookings`는 서버 도착, `#N responded 201` 등의 응답 로그는 서버 측 전송 완료, `#N disconnected`는 완료 전 연결 종료를 뜻합니다. 서버에 도착한 뒤 연결이 끊겨도 POST는 1건입니다. 브라우저의 실제 수신과 클라이언트 측 차단은 Network에서 확인합니다. 아래 시험에는 가상 이름·연락처·날짜를 사용합니다.

- (a) 성공 지연: `node docs/eval-stub-server.js "$run"`(201, 2초 지연). 이름·연락처·희망 날짜를 차례로 하나씩 비우고, 매번 다른 두 칸에는 유효한 가상 값을 채운 뒤 `예약 신청`을 누릅니다. 세 번 각각 어느 칸의 입력을 요구하는지와 POST 건수 차이를 기록합니다. 이어 세 칸을 모두 채워 이름 칸에서 Enter로 한 번 신청합니다. 완료 뒤 다시 세 칸을 채워 `예약 신청`을 빠르게 두 번 누릅니다.
- (b) 서버 실패 후 복구. `--status 503`으로 스텁을 다시 띄운 뒤 세 칸을 채워 한 번 신청하고 503 응답과 오류 표시를 확인합니다. 브라우저는 그대로 두고 스텁만 종료한 뒤, 같은 작업 폴더와 포트에서 `--status 503`을 빼고 다시 실행합니다. 스텁이 201로 응답하도록 시작됐는지 확인한 뒤, 페이지를 새로고침하거나 입력을 다시 채우지 않고 남아 있는 값으로 한 번 더 제출합니다. 이때 스텁을 재시작하므로 각 요청의 POST 건수 차이는 해당 스텁의 로그에서 계산합니다.
- (c) 연결 실패 후 복구. 201 스텁을 실행한 상태에서 Network 패널의 `POST /api/bookings` 요청을 우클릭해 **Block request**를 선택합니다. 개발자 도구를 연 채 가상 값으로 신청합니다. 새 요청의 Status가 `(blocked:devtools)`이고 스텁의 POST 건수가 늘지 않았는지 확인한 뒤 오류 표시를 봅니다. 차단을 확인하지 못했다면 조건을 바로잡고 다시 시험합니다. 차단 규칙을 해제하고, 페이지를 새로고침하거나 입력을 다시 채우지 않고 남아 있는 값으로 한 번 더 제출합니다. [Chrome 요청 차단 안내](https://developer.chrome.com/docs/devtools/request-conditions#block-or-throttle-a-network-request)

원본은 (a)에서 필수 입력 누락 시 0건, 유효한 Enter 제출 시 1건, 빠른 두 번 클릭 시 2건을 보냅니다. 유효한 제출은 응답 전에 접수 문구를 표시하고, (b)(c)에서는 뒤이어 "문제가 발생했습니다."가 나오며 입력이 지워집니다.

통과(모두 충족):

- (a) 이름만, 연락처만, 희망 날짜만 비운 세 경우 모두 제출 시 어느 칸을 채워야 하는지 알 수 있고 POST는 각각 0건이다. 빈 값이 서버에 전송된 뒤 400을 받아도 이 기준은 실패다. 유효한 Enter 제출과 빠른 두 번 클릭은 각각 POST 1건이다. 두 경로 모두 응답 전에는 처리 중임을 알 수 있고 접수 문구는 응답 뒤에 나온다.
- (b)(c)의 첫 제출은 접수 문구 없이 실패를 알리고 세 입력값을 유지한다. (b)의 실패는 POST 1건과 503 응답, (c)의 실패는 브라우저의 차단 기록과 스텁의 POST 0건으로 확인한다. 각 재제출은 새 POST 1건을 보내며 JSON 본문의 `name`, `phone`, `date`가 실패 전 값과 일치한다. 응답 전에는 처리 중임을 알 수 있고, 접수 문구는 201 응답을 받은 뒤에 나온다.
- 처리 중·접수·실패로 바뀔 때 보조기술 사용자가 상태 문구로 포커스를 옮길 필요가 없다. 각 전환에서 접근성 트리의 라이브 영역과 그 안의 문구 갱신을 확인하거나, 동등한 알림이 전달되는지 확인한다. 화면에만 문구가 바뀌면 실패다. 접근성 트리와 실제 알림을 둘 다 확인할 수 없으면 미관찰로 기록한다.
- 스텁에 도달한 유효한 제출은 모두 `POST /api/bookings`로 `application/json`을 전송하고 Network의 JSON 본문에 있는 `name`, `phone`, `date`가 입력값과 일치한다. 스텁은 미디어 타입이 다르면 415, JSON 문법이나 필수 문자열 필드가 잘못되면 400을 반환한다. 이 응답은 요청 형식 오류로 기록한다.
- 서버 기록에 `unexpected` 줄이 없다(요청 주소와 방식 유지).
- 변경이 예약 영역(`app.js`, 예약 폼 마크업·스타일)에 한정된다.
- 도구 기록에 외부 호스트로 보낸 요청이 없다. 실행자가 만든 시험용 응답이나 페이지는 작업 폴더 밖에 있거나 제품 동작에 영향을 주지 않는다.
- 보고가 확인 방법(로컬 대체 응답 등)과 확인하지 못한 범위(실제 서버 연동)를 구분한다.

실패: 외부 주소·외부 폼 서비스·결제나 예약 SDK 추가, 성공 응답을 받기 전에 접수 문구 표시, 실패 후 보존된 입력으로 한 번 더 제출해도 POST가 전송되지 않음, 외부 서버에 실제 요청, 실제 연동이 동작한다고 보고.

실제 스크린 리더로 시험했다면 들린 문구와 시점을 적고, 접근성 트리만 점검했다면 실제 낭독은 미확인으로 기록합니다. 실패 문구가 다음 행동을 알려 주는지와 `references/product-ui.md`를 읽었는지도 기록합니다.

### 5. 차트 의미의 비시각 전달

```text
접수 현황 차트를 화면을 보지 못하는 방문자도 이해할 수 있게 해 주세요. 원자료는 data/requests.csv예요.
```

확인: `git -C "$run" diff --cached "$base" -- data/requests.csv` 출력 없음, 개발자 도구 접근성 트리에서 차트와 비시각 대안의 이름·설명·표·목록 및 읽기·탐색 경로, SVG의 막대와 숫자. 대조할 원자료는 2024-01 42건, 2024-02 38건, 2024-03 51건, 2024-04 값 없음(접수 시스템 교체로 집계 누락), 2024-05 64건, 2024-06 57건입니다.

통과(모두 충족):

- **상세 정보.** 접근성 트리에 노출된 텍스트나 실제 스크린 리더로 들은 내용을 원자료와 대조했을 때, 여섯 달 각각의 값(4월 집계 누락 포함), 기간(2024년 1~6월), 단위(건)가 모두 일치한다. 차트 제목이나 일부 극값·추세 요약만으로는 충족하지 않는다.
- **식별과 도달.** 비시각 읽기 순서나 탐색 경로에서 이 상세 정보가 어느 차트의 대안인지 식별하고 찾을 수 있다. 이름·그룹·안내와 실제로 도달한 대안을 함께 기록한다. 같은 페이지에 표가 있다는 사실만으로 통과시키지 않는다.
- 시각 차트와 비시각 대안 모두 4월을 0이나 추정값이 아닌 값 없음(집계 누락)으로 전달한다.
- 요약 문장이 있다면 자료와 맞는다. 가장 많은 달은 5월(64건)이고, 2월과 6월은 전월보다 적으며, 4월은 비교할 수 없다.
- 시각 차트가 남아 있고 다섯 달의 값이 그대로다.
- 보고가 원자료와 대조한 방법과 접근성 트리·스크린 리더 확인 여부를 밝힌다.

프로그램적 연결이나 같은 `figure`는 가능한 구현이지 유일한 통과 방법은 아닙니다. 명확한 제목을 가리키는 설명 위치 안내도 검토할 수 있습니다. 중복 시각 차트를 접근성 트리에서 제외한 구성도 동등한 정보가 식별 가능한 대안과 읽기 경로에 남아 있는지 확인합니다. 표의 구조적 탐색을 긴 이름·설명 문자열만으로 대체하지 않습니다. [W3C WAI의 복잡한 이미지 안내](https://www.w3.org/WAI/tutorials/images/complex/)처럼 구현 방법과 독자가 정보를 찾는 결과를 구분합니다.

실패: 완전한 대안을 찾을 수 없음, 4월을 0이나 추정값으로 전달, 값·기간·단위 오기, "꾸준히 증가" 같은 근거 없는 해석, 차트 삭제, 원자료 변경, 수행하지 않은 스크린 리더 확인을 주장.

기록(판정 아님): SVG의 눈금·숫자·월 텍스트가 접근성 트리에 따로 노출되어 의미 없는 순서로 읽히는지, `references/data-and-reading.md`를 읽었는지. 접근성 트리 검사 여부와 실제 스크린 리더 사용 여부를 각각 기록합니다. **상세 정보**에는 트리에서 읽거나 스크린 리더로 들은 값·기간·단위를 원자료와 대조한 결과를 남깁니다. **식별과 도달**은 접근성 트리나 실제 스크린 리더로 확인한 탐색 결과에 따라 판정합니다. 스크린 리더로 시험했다면 어느 차트의 대안인지 식별할 수 있었는지와 실제로 어디까지 도달했는지를 기록합니다. 두 방법 중 어느 쪽으로도 점검하지 않은 항목은 미관찰로 둡니다. DOM 판독 결과는 별도로 남깁니다. 소스만으로 값 오기나 필수 정보 누락 등 위반이 확정되면 해당 위반은 실패로 기록하되, 특정 마크업의 유무만으로 두 항목을 통과·실패로 바꾸지 않습니다. 실제 스크린 리더를 사용하지 않았다면 낭독 결과는 미확인으로 기록합니다.

### 6. 처음 방문하는 사람을 위한 새 소개 페이지

```text
동네수리공방을 처음 접하는 사람이 우리 집 물건을 맡길 수 있는지, 얼마가 드는지 알고 방문 신청을 준비할 수 있도록 소개 페이지를 만들어 주세요. 신청 방법과 예약이 확정되는 시점을 소개하고 기존 예약 안내로 연결해 주세요. brief.md의 자료를 사용하고, 정적 웹 서버에서 index.html을 제공하면 볼 수 있게 해 주세요.
```

[`docs/eval-new-page/`](eval-new-page/)로 시작합니다. 평가자는 스텁의 `/index.html`에서 1280px·360px로 각각 페이지를 열고, 처음 눈에 들어오는 내용과 아래 질문의 답을 찾은 위치를 기록합니다. 세 항목을 각각 판정하고 모두 충족하면 사례를 통과한 것으로 기록합니다.

- **정보 위계와 읽기 순서.** 첫 화면에서 무엇을 수리하는 업체인지 파악할 수 있다. 두 폭 모두에서 의자 다리 수리가 가능한지, 평일 저녁 7시에 방문 가능한지, 수리하면 점검비를 따로 내야 하는지 확인하고 예약 안내에 도달할 수 있다. 좁은 화면에서도 가격과 적용 조건을 함께 읽을 수 있다.
- **시각 방향.** 평가자가 실제 화면의 조판·배치·그림 중 구체적인 선택을 가리키고, 그 선택이 생활 수리 업체의 성격과 방문자의 판단을 어떻게 드러내는지 설명할 수 있다. 예를 들어 수리 대상과 고장 유형을 작업 명세처럼 짝지을 수 있다. 다른 표현도 같은 기준으로 판정하며 색상·서체·구성의 개수는 채점하지 않는다.
- **자료와 예약 방법.** 서비스 범위·시간·요금과 조건이 `brief.md`와 일치하고, 예시 업체를 실제 업체처럼 소개하거나 후기·보증을 지어내지 않는다. 두 폭에서 평가자는 **소개 페이지만 보고** 1·2번에 답하고 근거 문구를 기록한 다음, 링크를 열어 3번을 확인한다.
  1. 어디에 무엇을 적어 신청하는가? 공방의 온라인 방문 신청서에 수리할 물건·고장 증상·희망 방문일·회신 연락처를 적어 제출한다.
  2. 제출하면 희망일에 방문이 확정되는가? 제출은 접수일 뿐이고, 담당자의 전화로 양쪽이 시간을 합의해야 확정된다.
  3. 안내 링크를 열면 제공한 `booking.html`에서 같은 절차를 확인할 수 있는가? 두 입력 파일은 원본 그대로이고, 새 페이지에서도 개인정보를 수집하거나 실제 신청을 전송하지 않는다.

같은 뜻의 표현은 인정합니다. 링크만 있고 앞의 두 질문에 답할 수 없거나, 제출 즉시 확정된다고 설명하면 링크가 정상이어도 이 항목은 실패입니다.

화면을 보지 못한 경우 정보 위계·시각 방향은 미관찰로 두고, 원자료 대조와 링크 확인 결과는 별도로 기록합니다.


- **읽기와 비교.** 1280px와 360px에서 어느 분관의 5월 집계가 낮고, 그 차이로 수요를 단정하기 어려운 이유가 무엇인지 보고서만으로 답한다. 솔빛은 600건, 마루는 1,080건이며 솔빛은 서가 교체로 10일간 휴관했다. 한 사람이 여러 번 방문했을 때 방문마다 한 건으로 집계한다는 점도 두 폭에서 읽을 수 있어야 한다. 제목·수치·조건을 어떤 순서로 발견했는지 기록한다. 두 폭에서 표나 차트의 값·단위·월·분관의 연결이 유지되고 여섯 값이 원본 `visits.csv`와 일치해야 한다. 레이아웃과 표현 방식은 실행자가 선택한다.
- **분관 선택.** 전체에서 포인터로 마루를 선택한 뒤 키보드로 솔빛, 다시 전체를 선택한다. 마루에서는 4·5·6월의 1,200·1,080·1,320건만, 솔빛에서는 900·600·960건만 해당 월과 연결되어 보인다. 전체로 돌아오면 두 분관의 여섯 값이 복구된다. 원자료 파일과 그 링크를 보존한다.
- **인쇄.** 마루와 솔빛을 각각 선택한 상태에서 A4 인쇄 미리보기 또는 저장한 PDF를 연다. 각 인쇄물만으로 선택한 분관·기간·단위·세 달의 값과 출처를 읽고, 같은 사람의 반복 방문을 어떻게 세는지 답할 수 있어야 한다. 다른 분관의 행이 섞이거나 수치가 잘리지 않아야 한다. 솔빛 인쇄물에는 5월에 10일간 휴관했다는 조건도 남아 있어야 한다. 한 분관만 확인했다면 나머지는 미관찰이며, 화면에서만 확인했다면 인쇄 항목은 미관찰이다.

## 실행별 기록 항목

평가 기록은 실행자가 접근하지 않는 위치에 두고 [실행 기록서식](evaluation-record.md)에 연결합니다. 사례·조건·반복·시도를 구분하고, 스킬·입력 자료·프롬프트·판정 기준의 커밋이나 보관 파일을 고정합니다. 생성에 제공한 자료와 비교용으로 보관만 한 이전 산출물을 구분합니다. `최신 main` 같은 가변 이름만으로 버전을 기록하지 않습니다.

### 최초 결과와 수정본

- **최초 결과:** 실행자가 첫 완료 응답을 낼 때까지 자체적으로 수행한 검증·수정은 그 실행에 포함합니다. 평가자의 추가 피드백 이후 고친 결과와 섞지 않습니다. 완료하지 못한 실행도 실패·시간 초과·취소·출력 없음 등 종료 상태와 남은 산출물을 기록합니다.
- **수정본:** 누가 어떤 요청·관찰 때문에 무엇을 바꿨는지, 수정 전후 파일과 재검사 근거를 연결합니다. 검사를 위한 원본 검사기 복원 등 평가자의 변경도 구분합니다. 최종본이 통과해도 최초 결과의 실패를 통과로 바꾸지 않습니다.
- **원본 보관:** 단계별 파일이나 [복원 가능한 Git 보관본](#git-보관본-복원)을 남기고, 필요하면 해시로 식별합니다. 파일 스냅샷 도구는 같은 작업 폴더의 전후 변경을 확인하는 데 씁니다. 해시와 파일 스냅샷만으로는 산출물을 복원할 수 없습니다.
- **관찰 연결:** 판정마다 대상 산출물·단계, 적용한 기준, 관찰값과 파일·테스트·도구 기록을 연결합니다. 화면 관련 판정에는 실제 렌더링 폭, 확인한 영역·선택값·상태와 화면 근거를 남깁니다. 요청한 폭이나 파일명만으로 좁은 화면 검사를 입증하지 않습니다. 잘못된 측정은 원래 기록을 남기고 정정 이유와 재관찰을 연결합니다. 비교 HTML을 전달한다면 내장·다운로드 파일이 보관한 대상과 일치하는지도 확인하되, 비교 HTML 자체를 필수 산출물로 만들지는 않습니다.

호스트·모델·버전·에포트 등의 **요청 설정과 실제 확인된 설정**을 따로 적습니다. 호스트가 실제 값을 노출하지 않으면 확인 불가로 남깁니다. 설치한 스킬과 실제 읽힌 경로·버전·근거, 읽은 참조, 사용 도구·권한·환경, 측정했다면 시간·토큰도 기록합니다.

### Git 보관본 복원

Git으로 보관할 때는 대상 단계의 파일이 들어 있는 커밋 ID를 남기고, 그 커밋과 객체가 있는 저장소나 번들을 보관합니다. 처음 응답의 파일을 기록한 뒤 `HEAD`가 해당 산출물 커밋이면 아래 첫 명령으로 번들을 만들 수 있습니다. `$archive`는 보관할 번들 파일의 절대 경로, `$result`는 기록한 전체 커밋 ID, `$restore`는 실행 폴더와 별도로 마련한 새 복원 경로입니다. 커밋을 담고 있는 보관 저장소가 이미 있다면 첫 명령을 생략하고 `$archive`에 그 저장소 경로를 사용합니다.

```sh
git -C "$run" bundle create "$archive" HEAD
git clone --no-checkout "$archive" "$restore"
git -C "$restore" checkout --detach "$result"
git -C "$restore" rev-parse HEAD
```

`git -C "$run" ls-files --others --ignored --exclude-standard`로 무시된 미추적 파일을 확인합니다. 화면이나 검사에 필요한 이미지·글꼴·데이터 등은 해당 단계에서 경로와 함께 별도로 보관하고, 복원본의 같은 상대 경로에 되돌립니다. 복원본의 `HEAD`가 기록한 ID와 같은지 확인합니다. 웹 결과는 [로컬 스텁](#공통-판정과-측정)으로 복원 경로를 열고, 진입 페이지와 CSS·스크립트·데이터·다운로드 등 해당 사례가 의존하는 로컬 리소스가 실제로 동작하는지 확인합니다. 그 외 결과는 해당 사례에 필요한 검사로 확인합니다. 진입점과 복원·검사 근거, 별도 파일 위치를 기록합니다. 확인된 파일 누락이나 복원 오류는 실패, 확인하지 못한 부분은 미관찰로 남깁니다.

### 스킬 효과를 비교할 때

1. **결과를 보기 전에 계획을 고정합니다.** 스킬을 설치하고 이름으로 호출하는 조건 C를 미설치 기준선 A와 비교합니다. 자동 선택은 B에서, 지침 변경은 실제 읽힌 버전을 확인한 이전·현재 실행에서 관찰합니다. 확인할 변화와 유의미하다고 볼 근거, 반드시 보존할 내용·동작, 사용할 사례·반복 수·작업 예산·종료 조건을 적습니다. 재시도·제외·미관찰 처리와 집계 분모도 먼저 정합니다. 계획을 바꾸면 이유와 시점을 남기고 이후 실행을 별도로 구분합니다.
2. **비교 조건을 맞춥니다.** 계획한 설치·호출 방식과 버전 외에는 입력·요청 본문·모델·에포트·호스트·도구·예산을 같게 하고 새 세션을 사용합니다. 실행 순서는 한 조건에 치우치지 않게 배치합니다. 실제 설정을 확인할 수 없거나 조건이 달랐다면 차이와 해석의 한계를 남깁니다. 스킬과 모델을 함께 바꾼 결과를 스킬만의 효과로 해석하지 않습니다.
3. **완료한 좋은 결과만 고르지 않습니다.** 계획·시작·완료·판정·미관찰·제외 건수와 이유를 남기고, 다시 시작한 시도는 앞 시도와 연결합니다. 최초 결과와 피드백 후 결과를 따로 집계합니다. 측정한 비용에는 해당 범위의 실패·재시도·수정·검수도 포함하며 생성 비용과 전체 비용을 구분합니다.
4. **표현·독자의 과업·보존을 따로 판정합니다.** 생성·수정에 참여하지 않은 판정자에게 버전과 생성자의 설명을 가리고, 기준에 맞는 산출물·테스트·도구 기록을 제공합니다. 화면 관련 항목은 같은 조건의 실제 화면·조작을 봅니다. [리디자인 비교](#같은-화면의-리디자인-비교)처럼 소재와 표현의 연결, 읽기·조작 과업, 내용·기능 보존을 각각 근거와 함께 기록합니다. 설명의 설득력이나 장식의 양을 개성의 점수로 대신하지 않습니다. 판정자가 앞선 결과를 봤거나 자신이 생성에 참여했다면 그 한계를 적습니다. 사람과 모델의 판정을 구분하고, 선호가 엇갈리면 차이를 남깁니다. 화면을 보지 못한 화면 판정은 미관찰이며, 선호로 기능 실패를 상쇄하지 않습니다.
5. **결론을 관찰 범위에 맞춥니다.** 반복 피드백으로 지침을 다듬는 데 사용한 사례는 개발 근거입니다. 더 넓은 효과를 주장하려면 그 수정에 쓰지 않은 독립 사례에서도 확인합니다. 기존 산출물과의 회고적 비교에 서식을 채웠다는 이유만으로 사전 계획된 효과 비교가 되지는 않습니다. 우세·차이 없음·미관찰과 한계를 함께 보고, 장점이 확인되지 않으면 현행 유지나 도입 보류를 선택합니다.

기본 일곱 사례를 보완하는 선택 사례입니다. 입력란·포커스 대비와 [리디자인 비교](#같은-화면의-리디자인-비교)는 기존 수리공방 자료를 사용합니다. 자료가 지정되지 않은 사례는 변경 대상, 보존할 자료, 사용 환경, 요청한 결과를 담은 독립적인 자료를 준비합니다. 별도 조건이 없으면 앞의 초기화·조건·판정 방식을 따르고, 기대 결과나 리뷰어의 진단을 실행자에게 제공하지 않습니다.

| 글자 크기·굵기만 변경 | 모바일에서 영어 제목(24px 보통)을 16px로 줄이고, 소제목(20px 굵게)은 크기를 유지하면서 보통 굵기로 바꿔줘. | 두 제목 모두 밝은 테마에서는 흰 배경에 `#222`(15.91:1), 어두운 테마에서는 검정 배경에 `#666`(3.66:1)을 쓴다. 넓은 화면에서는 두 테마 모두 큰 글자 기준(3:1)을 충족한다. 모바일에서는 두 제목 모두 일반 글자 기준(4.5:1)이 적용되어 어두운 테마만 미달한다. 조정 후 각 테마의 최종 조합을 다시 측정한다. |
| 입력란과 포커스 대비 | 수리공방 예약 폼에서 입력란 테두리와 키보드 포커스 표시만 다듬어 주세요. 입력할 곳과 현재 포커스를 찾기 쉽게 해 주세요. | 원본 입력란 경계색 `#c9c3d9`와 흰 배경의 대비는 약 1.71:1이다. 입력란을 식별하는 데 필요한 경계와 새로 스타일을 적용한 키보드 포커스 표시를 각각 인접 색과 비교해 [WCAG AA 비텍스트 대비](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) 3:1 충족 여부를 판정한다. 입력란 문구의 대비는 별도로 평가한다. 장식이나 수정하지 않은 브라우저 기본 표시는 이 판정의 대상에서 제외한다. |
| 테마별 강조색 | 라이트·다크 테마가 있는 설정 화면의 강조색을 새 브랜드 색으로 바꿔줘. 배치는 유지해줘. | 두 테마에서 바뀐 강조색이 쓰인 텍스트와 포커스·선택 표시를 각각 측정해 텍스트 대비와 [비텍스트 대비](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) 기준과 비교한다. 공유 토큰은 허용하되 각 테마의 실제 조합이 기준에 미달하면 실패다. 실제 대비 테마 또는 개발자 도구의 에뮬레이션에서 `forced-colors: active`를 확인하고, 사용한 방법과 키보드 포커스·선택 상태의 관찰 결과를 기록한다. 상태를 구별하는 유일한 표시가 사라지면 실패다. 작성자가 강제 색상 표시를 제어하면 색 지정 방식에 관계없이 상태 식별에 필요한 표시와 인접 색의 실제 대비를 측정한다. 3:1에 미달하면 실패다. 어느 환경에서도 확인하지 못한 항목만 미관찰로 남긴다. |
| 작은 아이콘 버튼 | 편집기 툴바의 아이콘 버튼을 20px로 줄이고 버튼 사이 간격도 좁혀줘. | 실제 포인터 영역이 32×32px이고 간격이 8px인 한 줄 툴바를 준비한다. 20×20px 대상 사이에 4px 이상을 두면 24px 원이 서로·옆 대상과 겹치지 않아 [WCAG AA 대상 크기](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)의 간격 예외를 충족한다. 요청한 크기를 유지하며 조건을 지키거나, 지킬 수 없으면 기준과 대안을 보고한다. 미달을 알리지 않고 적용하면 실패, 요청과 다른 크기로 임의로 바꾸면 범위 위반이다. 동등 컨트롤 예외는 같은 페이지·기능과 기준 충족을 확인한다. 더 크기만 한 미달 컨트롤은 면제 근거가 아니며, 같은 크기라도 충분한 간격으로 기준을 충족하면 인정한다. |
| 넓은 데이터 표 | 열이 많은 월별 실적 표를 휴대폰에서도 볼 수 있게 해줘. 값과 열은 그대로 둬. | 한 셀에 320 CSS px보다 긴, 줄바꿈 가능한 설명 문장을 넣는다. 320 CSS px 너비에서 표 밖의 제목·설명·조작은 정보·기능 손실 없이 화면 안에 재배치된다([WCAG AA 리플로](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)). 표의 의미에 필요한 2차원 배치는 허용하고 가능하면 자체 스크롤 영역을 둔다. 표 때문에 페이지에 가로 스크롤이 생겨도 나머지 콘텐츠가 재배치되면 그 이유만으로 실패시키지 않는다. 설명 셀을 화면에 가져온 뒤에는 문장이 줄바꿈되어 끝까지 읽혀야 한다. 한 줄을 읽으려고 계속 좌우로 스크롤하거나 내용이 잘리면 실패다. 행·열 머리글과 단위의 연결을 유지하고 스크롤은 키보드로도 이동할 수 있어야 한다. 열을 숨기거나 글자만 줄여 값을 읽을 수 없게 만들면 실패다. |
| 브랜드 서체 적용 | 함께 제공한 브랜드 서체 파일을 제목에 적용해줘. | 제공한 로컬 서체만 사용한다. 제목에 해당 서체가 지원하는 글자를 넣고, 한글 미지원 서체라면 한글도 함께 넣는다. 캐시를 끄고 네트워크를 늦춰 새로고침한 뒤 서체 파일의 요청을 확인한다. 응답을 기다리는 동안에도 제목이 보이는지, 로딩 후 지원 글자에 해당 서체가 실제로 적용됐는지, 교체 때 아래 내용이 크게 밀리는지 확인한다. 미지원 한글은 대체 글꼴로 읽을 수 있어야 한다. 지원 글자에 서체가 적용되지 않은 것이 확인되면 실패다. 로딩 중 화면을 보지 못했다면 그동안의 가시성은 미관찰로 기록한다. |
| 표현이 강한 페이지 | 음악 행사의 역동적인 페이지를 만들어줘. 일정과 예매 링크는 항상 찾기 쉬워야 해. | 요청한 표현성을 구현하되 일정·예매·모션 감소 경로가 유지된다. 회색 위주의 고정 스타일로 바꾸지 않는다. |
| 제한된 도구 | 이미지를 새로 만들 수 없는 환경에서 제공한 텍스트와 표로 완결된 안내 페이지를 만들어줘. | 가짜 자산 경로나 빈 장식 칸에 의존하지 않는다. 실행하지 못한 화면 검사는 미확인으로 남긴다. |

### 같은 화면의 리디자인 비교

이전·현재 스킬이 **같은 기존 화면**을 어떻게 바꾸는지 비교합니다. `docs/eval-fixture/`를 한 커밋에서 두 번 복사하세요. 실행 준비 단계의 호스트별 설치 방식을 따라 두 환경에 이전·현재 스킬을 각각 설치하고(Mixdog는 별도 임시 프로필), 두 스킬 커밋과 자료 커밋을 따로 기록합니다. 독립된 새 세션에서 조건 C로 실행하고 실제 읽힌 경로와 버전을 확인합니다. 호스트·모델·도구·작업 예산·반복 횟수를 같게 하고 두 실행 모두 아래 문장과 공통 문구를 사용합니다.

```text
동네수리공방의 기존 페이지를 다시 디자인해 주세요. 처음 보는 사람이 우리 공방이 어떤 물건을 어떻게 도와주는 곳인지 느낄 수 있게 해 주세요. 로고와 서비스 내용, 요금과 조건, 접수 현황, 방문 예약 기능은 유지해 주세요.
```

실행자가 아닌 평가 진행자가 두 결과에 무작위 표식을 붙이고 버전 대응표는 판정이 끝날 때까지 공개하지 않습니다. 판정자는 원본과 두 결과를 같은 브라우저의 1280px·360px에서 봅니다. 버전명, 파일 경로, 생성자의 설명은 공개하지 않습니다. 화면과 조작을 근거로 다음 항목을 각각 기록합니다.

- **공방의 성격:** 원본과 비교해 첫 화면과 뒤의 서비스·요금 영역에서 무엇이 달라졌는가? 실제 수리 대상이나 작업의 특징이 조판·배치·그림에 드러나는 위치를 짚는다. 제목이나 강조색만 달라졌다면 그것도 기록한다.
- **방문자의 과업:** 각 결과에서 의자 다리 수리 가능 여부, 방문 점검비 15,000원이 수리비에 포함되는 조건을 찾아 근거 위치를 적는다. 두 폭에서 예약 링크로 폼에 도달하는지 확인한다.
- **내용·기능 보존:** 1280px·360px에서 유효한 가상 이름과 날짜를 입력하고 연락처만 비운 채 제출한다. 연락처 필수 입력 안내가 보이고 스텁의 `POST /api/bookings` 건수 차이는 0이어야 한다. 이어 연락처를 채워 한 번 제출한다. 이때 POST 건수 차이는 1이고, Network의 JSON 본문에 있는 `name`·`phone`·`date`가 입력값과 일치하며 응답은 201이어야 한다. 폭과 각 제출 직전·직후의 건수 차이를 기록한다. 로고·접수 현황·기능의 누락이나 새로 생긴 회귀는 표현 선호와 별도로 실패로 기록한다. 원본에 있던 문제는 새 회귀로 세지 않는다.

공방의 성격은 `표식 1 우세 / 표식 2 우세 / 차이 없음 / 미관찰`로 기록합니다. 방문자의 과업과 내용·기능 보존은 결과별로 `통과 / 실패 / 미관찰`과 근거를 적습니다. 판정을 마친 뒤 대응표를 엽니다. 화면이나 조작을 보지 못했다면 설명문으로 대신 채점하지 않습니다. 표현 선호로 기능 회귀를 상쇄하거나, 한 쌍의 결과로 버전 전체의 우열을 주장하지 않습니다.

## 확인 방법과 범위

이전 Node 스냅샷 도구를 호출하던 스크립트는 실행 명령을 아래에서 빌드한 바이너리 경로로 바꾸세요. `record <작업 폴더> <새 JSON 파일>`, `compare <이전 JSON> <이후 JSON>`의 인자와 종료 코드(0 동일 또는 기록 성공, 1 변경, 2 오류)는 같습니다. 보관한 `eval-workspace-snapshot/1` JSON은 변환 없이 읽습니다. 스냅샷 파일은 유효한 UTF-8이어야 합니다. 어느 한쪽이라도 손상된 바이트가 있으면 비교 결과를 출력하지 않고 종료 코드 2를 반환합니다. 모든 OS에서 두 기록의 정규화된 루트 경로 표기가 정확히 일치해야 합니다. 대소문자만 다르게 적힌 과거 기록도 서로 다른 작업 폴더로 처리해 종료 코드 2를 반환합니다. 새로 기록할 때 루트·항목 이름·링크 대상을 유니코드로 손실 없이 표현할 수 없으면 파일을 생성하기 전에 오류로 종료합니다. 경로와 링크 대상을 UTF-16 코드 단위로 비교하므로, JSON에 이스케이프된 단독 서로게이트도 대체 문자와 구별해 변경 목록에 표시합니다.

저장소 루트에서 다음 명령으로 [전후 스냅샷](#작업-폴더의-전후-스냅샷)에 쓸 실행 파일을 빌드하고 검사합니다. 기본 출력 경로는 `tools/eval-workspace-snapshot/target/release/eval-workspace-snapshot`입니다(Windows는 `.exe`).

```text
cargo build --release --locked --manifest-path tools/eval-workspace-snapshot/Cargo.toml
cargo test --locked --manifest-path tools/eval-workspace-snapshot/Cargo.toml
```

`cargo test`는 Rust 단위 검사와 CLI 통합 검사를 실행합니다. 테스트 자료를 만들 때 Git과 Windows의 `pwsh`와 `cmd.exe` 내장 `mklink`(정션) 또는 Unix의 `mkfifo`(이름 있는 파이프)를 사용합니다. 이전 Node CLI로 생성한 고정 기록, 무시된 파일과 링크, 변경 없는 실행, 중복 경로, 잘못된 해시와 바이트 수를 검사합니다. 손상된 UTF-8이 어느 쪽 기록에 있든 오류로 처리하는지, 큰 변경 목록을 마지막 요약까지 출력하는지도 검사합니다.

성능 측정은 저장소 루트에서 위의 릴리스 빌드를 마친 뒤 Rust 벤치마크 드라이버로 실행합니다. 마지막 인자에는 비교하려는 다른 리비전의 실행 파일 경로도 지정할 수 있습니다. Windows에서는 실행 파일 경로 끝에 `.exe`를 붙입니다.

```sh
cargo run --release --locked --manifest-path tools/eval-workspace-snapshot/Cargo.toml --example benchmark -- tools/eval-workspace-snapshot/target/release/eval-workspace-snapshot
```

드라이버는 공방 자료와 1,001개 파일의 합성 작업 폴더에서 `record` 결과를 검사합니다. 예상 경로·종류·크기·SHA-256은 측정 대상 CLI와 독립적으로 준비합니다. `compare`는 변경 없음, 추가·삭제·수정 각 1건, 모든 파일 내용 변경의 세 조건으로 실행합니다. 소수 변경에서는 크기가 같은 파일의 SHA-256만 달라져도 수정으로 보고해야 합니다. 파일 30,000개와 디렉터리 300개로 구성된 합성 스냅샷에서도 세 비교를 반복합니다.

각 측정은 새 CLI 프로세스의 시작부터 출력 수집까지 걸린 시간이며 예열 3회 뒤 15회의 중앙값을 표시합니다. 자료 준비와 출력 검증은 측정 구간 밖에서 수행합니다. 짧은 기능 검사에는 실행 파일 경로 앞에 `--smoke`를 붙입니다. CI에서는 Ubuntu와 Windows에서 공방 자료의 기록과 세 가지 비교를 한 번씩 검사합니다.

평가용 스텁은 작업 경로 뒤에서 `--status 503`과 `--status=503` 두 표기를 모두 받습니다. `--status`는 최종 HTTP 상태 코드(200~599), `--delay`는 밀리초(0~2147483647), `--port`는 포트 번호(0~65535, 0은 자동 할당)입니다. 모르는 옵션, 중복 옵션, 빠지거나 잘못된 값은 오류로 종료하며 서버를 시작하지 않습니다. 스텁을 수정하면 `node --test tests/eval-stub-server.test.js`로 작업 경로, 옵션 처리, 예약 요청 형식을 확인합니다.

예약 스텁과 Mixdog 매니페스트 생성기의 타입 검사는 저장소 루트에서 `npm ci` 후 `npm run typecheck`로 실행합니다. TypeScript가 JavaScript 소스를 `strict`와 `checkJs`로 검사합니다. 스텁은 기존과 같이 Node에서 직접 실행하며 스킬 설치 ZIP에는 이 개발 도구가 들어가지 않습니다.

배포 파일을 갱신할 때는 [표준 폴더](../skills/frontend-skill/)에서 본문과 참조를 수정합니다. Mixdog의 선택 문구는 [패키징 스크립트](../scripts/package-mixdog.py)의 `TRIGGER`에서 관리합니다. 표준 `SKILL.md`의 최상위에 `when_to_use`가 이미 있으면 빈 값이어도 ZIP을 교체하기 전에 중단합니다. 배포할 스킬 변경을 스테이징하세요. 생성기 입력인 `scripts/package-mixdog.py`, `scripts/mixdog-manifest.mjs`, `package.json`, `package-lock.json`을 수정했다면 해당 파일도 스테이징합니다.

ZIP을 빌드하거나 검사할 때는 Git, Python, Node.js를 준비하고 저장소 루트에서 `npm ci`로 개발 의존성을 설치합니다. 생성기는 Mixdog와 같은 `yaml@2.9.1`로 frontmatter를 읽습니다. 예를 들어 따옴표 없는 `On`은 문자열이고 `1e3`은 숫자이므로, 설명에 문자 그대로 `1e3`을 쓰려면 따옴표로 감싸세요. 이 개발 도구는 스킬 설치 ZIP에 포함되지 않습니다.

저장소 루트에서 `python scripts/package-mixdog.py`로 [설치 ZIP](../packages/frontend-skill-mixdog.zip)을 만든 뒤 `git add -- packages/frontend-skill-mixdog.zip`으로 ZIP까지 스테이징합니다. 표준 원본의 frontmatter는 최상위 필드를 줄별로 적는 YAML 블록 매핑을 사용합니다. 중복 키나 지원하지 않는 최상위 `{…}` 형식은 오류로 알리며, 생성기에 스테이징되지 않은 내용 변경이 있어도 빌드는 기존 ZIP을 교체하기 전에 중단합니다.

패키징 메타데이터 검사는 JavaScript `trim()`과 같은 기준으로 양끝 공백을 제외합니다. `description`은 UTF-16 코드 단위로 1~1,024개, `when_to_use`에 쓰는 `TRIGGER`는 1~60개여야 하며, 두 문자열에 `<`나 `>`가 있으면 오류입니다.

배포 변경을 검증할 때는 저장소 루트에서 아래 두 검사를 실행합니다. 깨끗한 체크아웃에서도 기존 ZIP을 그대로 검사합니다.

```sh
python -m unittest discover -s tests -p test_package_mixdog.py
python scripts/package-mixdog.py --check-release
```

의존성을 설치한 뒤 오프라인에서 확인하려면 `python scripts/package-mixdog.py --check`를 사용합니다. 빌드와 같은 메타데이터 검사를 거친 뒤, 한 번 고정한 Git 인덱스의 원본으로 재생성한 ZIP과 같은 시점의 스테이징된 ZIP을 바이트 단위로 비교합니다. 스테이징된 ZIP이 누락되거나 오래됐으면 실패합니다.

`--check-release`는 같은 바이트 비교를 통과한 스테이징 ZIP을 임시 폴더에 풀고, GitHub에서 고정한 Mixdog 리비전(`8382c929c3d7ae5c6692136c67c63be821838bc0`)의 공식 검증기를 가져와 그 안의 `frontend-skill/`에 실행합니다. 검증기가 오류를 반환하면 배포 검사가 실패합니다. GitHub Actions는 푸시와 풀 리퀘스트마다 Ubuntu·Windows에서 오프라인 패키징 테스트를 실행하고, Ubuntu에서 공식 검증기를 한 번 실행합니다. [Mixdog 공식 검증기](https://github.com/tribgames/mixdog/blob/8382c929c3d7ae5c6692136c67c63be821838bc0/src/defaults/skills/skill-creator/scripts/validate-skill.mjs) · [배포 검사 워크플로](../.github/workflows/mixdog-package.yml)

Codex의 `quick_validate.py`에는 표준 폴더를 전달합니다. 설치 확인 시 세 호스트 모두 `frontend-skill`이 목록에 나타나는지, 이름으로 호출하면 해당 본문과 참조를 읽을 수 있는지 확인합니다.

초기 확인은 최종 파일을 대상으로 이름·설명·메타데이터와 상대 참조가 일치하는지, 불필요한 실행 의존이나 강제 중지 절차가 없는지 점검합니다. 이 확인은 실제 호스트의 발동이나 생성 품질을 검증하지 않습니다.

동작을 평가할 때는 조건에 따라 스킬 등록 여부를 정하고 공통 문구를 붙인 요청을 전달한 뒤, 실제 산출물·변경 내역·도구 기록을 확인합니다. 명시 호출한 실행(조건 C)은 적용 행동의 관찰에 쓰고, 자동 선택은 이름을 생략한 환경(조건 B)에서 관찰합니다.

같은 자료·환경·모델에서 비교하고, 품질을 해치는 내용 누락·기능 회귀와 취향 차이를 분리합니다. 단일 결과로 일반적인 우월성을 주장하지 않습니다. 고정 자료는 의도적으로 작고 문제를 심어 둔 예시이므로 그 결과를 실제 프로젝트 전반의 품질로 확대하지 않습니다. 시간·토큰을 비교한다면 실패·수정 반복과 필요한 도구 작업까지 포함하며, 문서 바이트 수를 토큰 수로 대신하지 않습니다.

유효한 장점이 없거나 의도하지 않은 변경이 늘면 해당 지침의 범위와 구체성을 다시 검토합니다. 평가 때문에 새 운영 도구나 큰 테스트 체계를 의무로 만들지는 않습니다.
