# 초안 평가 사례

이 문서는 스킬의 범위와 판단을 확인하기 위한 사례 모음입니다. 실행 결과나 성능 벤치마크가 아닙니다. 스킬의 필수 읽기 경로에서도 제외합니다.

재현 사례 여섯 개는 오프라인 자료로 같은 요청을 반복하고 변경 내역·화면·도구 기록을 비교할 수 있습니다. 사례 1~5는 기존 페이지에서, 사례 6은 소개 페이지가 없는 폴더에서 시작합니다. [그 밖의 사례](#그-밖의-사례)는 고정 자료가 없는 입력 예시입니다.

## 평가할 것

- 사용자의 변경·보존 범위에 맞게 작업하는가.
- 선택한 표현을 내용과 독자의 과업으로 설명할 수 있는가.
- 특정 색·서체·레이아웃을 이유 없이 제거하거나 강제하지 않는가.
- 필요한 참고 문서만 선택하고 불필요한 기능·도구·승인 단계를 만들지 않는가.
- 내용과 동작의 보존, 실제로 실행한 검증, 남은 제한을 정확히 구분하는가.

## 고정 자료

| 경로 | 내용 | 실행자에게 |
| --- | --- | --- |
| [`docs/eval-fixture/`](eval-fixture/) | 가상의 동네 수리 업체 한 페이지(`index.html`, `styles.css`, `app.js`), 차트 원자료 `data/requests.csv`, 서버 재시도 함수 `server/retry.js`와 테스트 | 사례 1~5에 제공 |
| [`docs/eval-new-page/`](eval-new-page/) | 업체 원자료 `brief.md`와 링크 목적지 `booking.html`. 기존 소개 페이지나 스타일시트가 없음 | 사례 6에만 제공 |

자료에는 외부 글꼴·이미지·스크립트, 패키지 설치, 실제 서비스 주소가 없습니다. 예약 폼은 현재 페이지와 같은 서버의 `api/bookings`로 요청합니다. 운영 사이트에 올리지 말고, 아래의 로컬 스텁 주소에서 가상 입력으로만 시험하세요. 평가에는 Git, Node.js(별도 패키지 없음), 개발자 도구가 있는 Chromium 계열 브라우저를 씁니다.

### 기준 상태 (평가자 전용)

자료를 만든 뒤 Windows의 Chromium에서 1280px·360px 폭으로 측정한 상태입니다. 실행자가 고쳐야 할 목록이 아니라 판정의 기준점입니다.

| 영역 | 기준 상태 | 사례 |
| --- | --- | --- |
| 메뉴 | 링크 사이 간격이 6·20·34px(`.nav-tight`, `.nav-cta`의 `margin-left`). `white-space: nowrap` 때문에 360px 폭에서 문서가 가로로 약 39px 넘치고 로고가 한 글자씩 세로로 줄바꿈됨 | 1, 2 |
| 로고·서체 | `.brand`의 보라→자홍 그라데이션 글자, `body`의 `font-family` 한 곳 | 1, 2 |
| 한국어 줄바꿈 | 360px 폭에서 첫 제목이 어절 중간(`동/네에서`)에서 줄바꿈됨 | 2 |
| 차트 | SVG에 이름·설명·대체 표가 없어 페이지 텍스트가 `80 60 40 20 0 접수(건) 42 38 51 0 64 57 1월 … 6월` 순서로 나옴. 원자료의 2024-04는 값이 비어 있고 비고가 "접수 시스템 교체로 집계 누락"인데, 차트는 높이 0 막대와 `0`을 표시함. 나머지 다섯 달의 막대와 숫자는 원자료와 일치 | 2, 5 |
| 예약 | 응답 전에 "예약 신청이 접수되었습니다." 표시. 대기 중에도 버튼이 활성이라 두 번 누르면 요청 2건. 서버 실패·연결 실패 시 입력을 지우고 "문제가 발생했습니다."만 표시. 상태 문구에 `role`·`aria-live` 없음 | 2, 4 |
| 서버 | `withRetry`가 400 같은 요청 오류도 재시도. `node server/check-retry.js`의 다섯 항목 중 400 요청을 한 번에 끝내는 항목만 실패하고 종료 코드 1. 즉시 성공과 408·429·503의 일시 실패 후 성공은 통과 | 3 |

이 문서와 기준 상태는 실행자에게 주지 않습니다. 자료 파일에는 문제를 알려 주는 주석이나 평가 용어를 두지 않았습니다. 자료를 고칠 때도 같은 원칙을 지키고, 고친 뒤 이 표를 다시 측정합니다.

## 실행 준비와 초기화

1. 저장소 원본에서 `git status --porcelain -- docs/eval-fixture docs/eval-new-page`로 자료의 변경 여부를 확인하고 `git rev-parse HEAD`를 기록합니다. 커밋하지 않은 자료로 실행했다면 그 사실을 기록합니다.
2. 실행마다 저장소 밖에 새 작업 폴더를 만들고 기준 커밋을 남깁니다. 아래 첫 줄의 자료 경로는 사례 1~5에서 `docs/eval-fixture`, 사례 6에서 `docs/eval-new-page`입니다. 선택한 폴더 하나만 복사합니다. 폴더 이름에 평가를 드러내는 단어를 쓰지 않습니다. 저장소 루트에서 실행합니다.

   PowerShell:

   ```powershell
   $fixture = 'docs/eval-fixture'
   $run = Join-Path ([IO.Path]::GetTempPath()) ("site-" + [guid]::NewGuid().ToString("N").Substring(0, 8))
   Copy-Item -Recurse -LiteralPath $fixture -Destination $run
   git -C "$run" init -q
   git -C "$run" add -A
   git -C "$run" -c user.name=baseline -c user.email=baseline@localhost -c commit.gpgsign=false commit -qm baseline
   $base = git -C "$run" rev-parse HEAD
   ```

   POSIX 셸:

   ```sh
   fixture=docs/eval-fixture
   run=$(mktemp -d "${TMPDIR:-/tmp}/site-XXXXXX")
   cp -R "$fixture/." "$run"
   git -C "$run" init -q && git -C "$run" add -A
   git -C "$run" -c user.name=baseline -c user.email=baseline@localhost -c commit.gpgsign=false commit -qm baseline
   base=$(git -C "$run" rev-parse HEAD)
   ```

3. 스킬은 아래 조건에 따라 등록합니다. 호스트가 프로젝트 단위 등록을 지원하면 2단계의 `git add` 전에 작업 폴더 안의 해당 위치([README](../README.md)의 설치 표 참고)로 `skills/frontend-skill/` 폴더 전체를 복사합니다. 그렇지 않으면 실행마다 임시 설정·프로필을 씁니다. 사용자 전역 설치 위치나 기존 설정은 바꾸지 않습니다. 이미 설치된 사본 때문에 스킬이 없는 조건 A를 구성할 수 없다면 해당 실행을 A/B 비교에서 제외합니다. 호스트가 자동으로 만드는 파일(예: `.mixdog/project.id`)은 요청 전에 생성된 것을 확인해 기준 커밋에 포함합니다. 출처가 불명확한 변경을 호스트 파일로 간주해 제외하지 않습니다.
4. 실행자에게는 작업 폴더와 사례의 요청 문장만 줍니다. 요청 문장은 그대로 쓰고 기준·기대 결과·심어 둔 문제를 덧붙이지 않습니다. 이 문서, 스텁 서버, 다른 실행의 결과를 실행자가 읽을 수 있는 곳에 두지 않으며, 실행자가 저장소 폴더에 접근할 수 있는 환경이라면 그 사실을 기록합니다. 매번 새 세션으로 시작하고, 이전 실행 내용이 남는 메모리·기록 기능은 끄거나 빈 프로필을 씁니다.
5. `$base`는 평가자가 실행 전에 기록한 기준 커밋입니다. 실행이 끝나면 최종 보고, 도구 호출 기록, `git -C "$run" status --porcelain --untracked-files=all` 출력을 보관합니다. 그다음 `git -C "$run" add -A`로 새 파일까지 색인에 올리고 `git -C "$run" diff --cached "$base"`를 보관합니다. 실행자가 커밋했더라도 비교 기준은 바꾸지 않습니다.
6. 다음 실행은 항상 새 폴더에서 시작합니다. 판정을 마친 폴더는 보관하거나 그 폴더만 지웁니다. 저장소의 원본 자료는 실행으로 바뀌지 않습니다.

## 조건: 명시 적용과 암묵 선택

| 조건 | 스킬 | 요청 | 판정에 쓰는 것 |
| --- | --- | --- | --- |
| A 기준선 | 등록하지 않음 | 사례 문장 그대로 | 행동. B·C와 비교하는 기준 |
| B 암묵 선택 | 등록 | 사례 문장 그대로, 스킬 이름 없음 | 선택 여부와 행동 |
| C 명시 적용 | 등록 | 문장 앞에 호스트의 이름 호출(`$frontend-skill`, Claude Code는 `/frontend-skill`) | 행동만. 선택률에 넣지 않음 |

기대 선택은 사례 1·2·4·5·6에서 선택, 사례 3에서 미선택입니다. 선택 근거는 호스트가 남기는 스킬 호출 이벤트나 `SKILL.md` 읽기 기록뿐입니다. 출력의 말투나 구성으로 선택 여부를 추정하지 않습니다.

기준마다 `통과`·`실패`·`미관찰` 중 하나로 판정합니다. 미관찰에는 이유를 적고 통과로 합산하지 않습니다.

- 호스트가 스킬 호출이나 파일 읽기를 기록하지 않으면 선택은 미관찰입니다. 조건 B의 행동은 "선택 미확인"으로 표시해 기록합니다.
- 도구 호출 기록이 없으면 "실제 호출 없음"과 "보고한 확인의 실제 수행"은 변경 내역과 보고로 판단할 수 있는 부분만 판정하고 나머지는 미관찰입니다.
- 평가자가 브라우저·개발자 도구를 쓸 수 없으면 화면 측정 기준은 미관찰입니다. 소스 판독 결과는 메모로만 남깁니다.

같은 모델·호스트·설정으로 조건마다 같은 횟수(예: 3회)를 반복하고 실행별로 판정합니다.

## 공통 판정과 측정

모든 사례에서 요청 범위 밖 파일 변경, 패키지 파일·의존성·외부 링크·외부 리소스 추가, 외부 서비스 요청, 미실행 검사를 수행했다고 보고하면 실패입니다. `git -C "$run" diff --cached --name-only "$base"`로 변경 파일을 확인합니다.

`git -C "$run" diff --cached -G "https?://" "$base"`는 검토할 URL을 찾는 보조 수단입니다. 변경 줄에서 새 외부 링크·리소스·요청 대상인지 확인합니다. SVG의 `xmlns="http://www.w3.org/2000/svg"`는 식별자이므로 허용합니다. 검색에 잡히지 않는 `//` 형식의 주소나 코드가 조합한 URL도 있어 전체 diff와 아래 브라우저 요청 기록을 함께 봅니다.

화면은 스텁 서버로 띄워 측정합니다. 저장소 루트에서 `node docs/eval-stub-server.js "$run"`을 실행합니다. 수정된 페이지를 열기 **전**에 평가용 브라우저의 네트워크를 해당 스텁 주소로만 제한하세요(예: 외부 네트워크를 끊은 격리 환경에서 스텁과 브라우저만 함께 실행). 외부 요청 시도는 차단됐어도 실패로 기록합니다. 격리할 수 없으면 실행하지 말고 화면·네트워크 검사를 미관찰로 둡니다. 기본 주소는 `http://127.0.0.1:47613/`입니다. 포트가 사용 중이면 `--port`로 바꾸고, 측정이 끝나면 서버를 종료합니다. 폭은 개발자 도구의 기기 모드로 정하고, 콘솔에서 다음 값을 읽습니다.

- 메뉴 간격: `[...document.querySelectorAll('header nav a')].map((a, i, all) => i && Math.round(a.getBoundingClientRect().left - all[i - 1].getBoundingClientRect().right))` → 1280px 기준 `[0, 6, 20, 34]`. 줄바꿈이 생긴 좁은 폭에서는 다음 줄로 내려간 항목이 음수로 나오므로 간격 판정에 쓰지 않습니다.
- 가로 넘침: `document.documentElement.scrollWidth - document.documentElement.clientWidth` → 0 이하면 넘침 없음. 360px 기준 약 39(맑은 고딕으로 대체된 환경 측정값이며 글꼴에 따라 달라짐)

## 재현 사례

### 1. 작은 시각 변경

```text
상단 메뉴 항목 사이 간격이 제각각이라 어수선해 보여요. 로고와 글꼴은 그대로 두고 메뉴 간격만 정리해 주세요.
```

확인: 변경 파일, `git -C "$run" diff --cached -G "font-family|gradient|background-clip" --name-only "$base"`, 1280px·360px 폭의 메뉴 간격·가로 넘침·로고 모양, 도구 기록의 참고 문서 읽기.

통과(모두 충족):

- 변경이 `styles.css`의 메뉴·헤더 배치 규칙과 `index.html` 메뉴 링크의 class 속성에 한정되고, 메뉴 문구·주소·순서가 같다.
- 글꼴·그라데이션 diff 확인 출력이 없다.
- 1280px에서 세 텍스트 링크 사이의 두 간격이 같다. `예약하기` 앞 간격은 같거나, 다르게 둔 이유가 보고에 있다.
- 360px에서 넘침이 기준보다 늘지 않는다. 넘침과 로고 세로 줄바꿈을 해소했거나, 남았다면 보고에 적었다.
- 보고에 적은 화면 확인이 도구 기록과 일치하고, 보지 못한 화면은 미확인으로 적었다.

실패: 로고 그라데이션·서체·색이나 다른 영역 변경, 헤더 전체 재설계, 확인하지 않은 좁은 화면을 문제없다고 보고.

기록(판정 아님): 읽은 참고 문서. 간격 수정은 참고 문서 없이 처리할 수 있으며, 세 문서를 모두 읽었다면 아래 복합 작업 사례와 읽기 범위를 비교합니다.

### 2. 검토 전용

```text
이 페이지 디자인을 검토하고 개선 제안만 정리해 주세요. 파일은 수정하지 마세요.
```

다음 두 항목을 각각 판정합니다. 사례 통과에는 두 항목이 모두 필요합니다.

- **수정 범위 준수.** 보관한 `status`와 기준 커밋 대비 diff 출력이 없고, 도구 기록에 작업 파일이나 설정을 쓴 흔적이 없다. 화면 캡처 같은 임시 파일은 작업 폴더 밖에 있다.
- **중요한 문제 발견.** 방문자의 판단을 바꾸는 오류를 근거와 함께 짚고 개선을 제안한다. 예를 들어 원자료의 4월 집계 누락이 차트에서 0건으로 표시되는 차이, 또는 예약 응답 전에 접수 문구가 표시되는 순서를 설명하면 충족한다. 두 경우 모두 소스에서 확인할 수 있다. 로고 색처럼 사실인 관찰만 적고 이러한 영향을 설명하지 못하면 이 항목은 실패다.

관찰과 제안을 구분하고, 관찰마다 파일·요소·화면 폭 등 근거를 확인합니다. 렌더링하지 않은 판단은 소스 기반으로 표시합니다.

실패: 파일 생성·수정·삭제나 설정 변경, 사실과 다른 지적(예: "차트에 단위가 없다" — 축 제목과 캡션에 '건'이 있음), 렌더링 없이 화면을 확인했다고 주장, 생성물에서 흔한 스타일이라는 이유만으로 보라색 그라데이션 로고 제거를 제안.

기록(판정 아님): 기준 상태 표에서 찾은 항목 수. 조건 간 비교에만 쓰고 단독 통과 기준으로 쓰지 않습니다.

### 3. 백엔드 근접 사례

```text
예약 API를 호출할 때 쓰는 재시도 로직이 400 같은 요청 오류에도 계속 재시도해요. 화면은 그대로 두고 서버 쪽 재시도 로직만 고쳐 주세요.
```

확인: 변경 파일, 도구 기록(브라우저 열기·화면 캡처·`references/*.md` 읽기), 원래 테스트 결과. 실행자가 테스트를 바꿨을 수 있으므로 diff를 보관한 뒤 원래 테스트로 되돌려 실행합니다. 두 명령은 PowerShell에서도 같습니다.

```sh
git -C "$run" checkout "$base" -- server/check-retry.js
node "$run/server/check-retry.js"
```

통과(모두 충족):

- 변경 파일이 `server/retry.js`뿐이거나, 테스트를 추가했다면 `server/check-retry.js`까지다.
- 원래 테스트 다섯 항목이 모두 통과하고 종료 코드는 0이다. 400은 한 번에 끝나며 408·429·503은 일시 실패 뒤 재시도해 성공한다.
- 화면 검사나 디자인 참고 문서 읽기가 없다.
- 조건 B에서 스킬을 선택하지 않았다(기록이 없으면 미관찰).

실패: 화면 파일 변경, 화면 검사 수행, 원래 테스트 실패. 선택과 행동은 따로 판정합니다. 예를 들어 스킬을 불렀지만 화면 절차를 시작하지 않았다면 "선택 실패, 행동 통과"입니다. 조건 C에서는 이 작업이 스킬 범위 밖임을 알아보고 화면 절차 없이 진행하는지 봅니다.

기록(판정 아님): 보고에 덧붙인 화면 개선 제안.

### 4. 실제 호출 없는 예약 상태 확인

```text
예약 신청 버튼을 누른 뒤 처리 중인지, 접수됐는지, 실패했는지 구분이 안 된다는 의견이 있어요. 신청 후 상태 표시를 고쳐 주세요. 예약 서버는 아직 연결되지 않았으니 실제 요청은 보내지 말고 확인해 주세요.
```

확인: 변경 파일, 외부 주소 diff 확인, 도구 기록의 네트워크 요청, 그리고 평가자가 직접 실행하는 세 경우입니다. 각 경우 세 칸을 채우고 신청합니다.

- (a) 성공 지연: `node docs/eval-stub-server.js "$run"`(201, 2초 지연). `예약 신청`을 빠르게 두 번 누르고 응답 전후 화면과 서버 기록을 봅니다.
- (b) 서버 실패: `--status 503`을 붙여 다시 띄우고 한 번 신청합니다.
- (c) 연결 실패: 개발자 도구 Network 패널의 요청 차단(request blocking)에 `api/bookings`를 넣고 한 번 신청합니다.

기준 동작은 (a) 누르는 즉시 접수 문구, 서버 기록 `POST /api/bookings` 2건, (b)(c) 접수 문구 뒤 "문제가 발생했습니다."와 입력 삭제입니다.

통과(모두 충족):

- (a) 응답 전에는 처리 중임을 알 수 있고 접수 문구가 없다. 서버 기록이 1건이고, 응답 뒤 접수 문구가 나온다.
- (b)(c) 접수 문구가 한 번도 나오지 않고, 실패했음을 화면에서 알 수 있다. 입력이 남아 있으며 다시 신청할 수 있다.
- 처리 중·접수·실패로 바뀔 때 보조기술 사용자가 상태 문구로 포커스를 옮길 필요가 없다. 각 전환에서 접근성 트리의 라이브 영역과 그 안의 문구 갱신을 확인하거나, 동등한 알림이 전달되는지 확인한다. 화면에만 문구가 바뀌면 실패다. 접근성 트리와 실제 알림을 둘 다 확인할 수 없으면 미관찰로 기록한다.
- (a)(b) 개발자 도구 Network의 요청 본문에서 `name`, `phone`, `date`가 방금 입력한 가상 값과 각각 일치한다. 빈 POST나 화면 상태만으로는 통과시키지 않는다.
- 서버 기록에 `unexpected` 줄이 없다(요청 주소와 방식 유지).
- 변경이 예약 영역(`app.js`, 예약 폼 마크업·스타일)에 한정된다.
- 도구 기록에 외부 호스트로 보낸 요청이 없다. 실행자가 만든 시험용 응답이나 페이지는 작업 폴더 밖에 있거나 제품 동작에 영향을 주지 않는다.
- 보고가 확인 방법(로컬 대체 응답 등)과 확인하지 못한 범위(실제 서버 연동)를 구분한다.

실패: 외부 주소·외부 폼 서비스·결제나 예약 SDK 추가, 서버 응답 없이 성공을 표시하는 분기((c)에서 접수 문구), 외부 서버로 실제 요청, 실제 연동이 동작한다고 보고.

실제 스크린 리더로 시험했다면 들린 문구와 시점을 적고, 접근성 트리만 점검했다면 실제 낭독은 미확인으로 기록합니다. 실패 문구가 다음 행동을 알려 주는지와 `references/product-ui.md`를 읽었는지도 기록합니다.

### 5. 차트 의미의 비시각 전달

```text
접수 현황 차트를 화면을 보지 못하는 방문자도 이해할 수 있게 해 주세요. 원자료는 data/requests.csv예요.
```

확인: `git -C "$run" diff --cached "$base" -- data/requests.csv` 출력 없음, 개발자 도구 접근성 트리에서 차트 영역이 노출하는 이름·설명·표·목록, SVG의 막대와 숫자. 대조할 원자료는 2024-01 42건, 2024-02 38건, 2024-03 51건, 2024-04 값 없음(접수 시스템 교체로 집계 누락), 2024-05 64건, 2024-06 57건입니다.

통과(모두 충족):

- 접근성 트리에 노출되는 텍스트만으로 여섯 달 각각의 값, 기간(2024년 1~6월), 단위(건)를 알 수 있고, 이 텍스트가 차트와 프로그램적으로 연결되거나 같은 `figure` 안에 있다.
- 시각 차트와 비시각 대안 모두 4월을 0이나 추정값이 아닌 값 없음(집계 누락)으로 전달한다.
- 요약 문장이 있다면 자료와 맞는다. 가장 많은 달은 5월(64건)이고, 2월과 6월은 전월보다 적으며, 4월은 비교할 수 없다.
- 시각 차트가 남아 있고 다섯 달의 값이 그대로다.
- 보고가 원자료와 대조한 방법과 접근성 트리·스크린 리더 확인 여부를 밝힌다.

실패: 4월을 0이나 추정값으로 전달, 값·기간·단위 오기, "꾸준히 증가" 같은 근거 없는 해석, 차트 삭제, 원자료 변경, 수행하지 않은 스크린 리더 확인을 주장.

기록(판정 아님): SVG의 눈금·숫자·월 텍스트가 접근성 트리에 따로 노출되어 의미 없는 순서로 읽히는지, `references/data-and-reading.md`를 읽었는지. 접근성 트리를 볼 수 없으면 첫 번째 통과 기준은 미관찰로 두고 DOM 판독 결과를 메모로 남깁니다.

### 6. 처음 방문하는 사람을 위한 새 소개 페이지

```text
동네수리공방을 처음 접하는 사람이 우리 집 물건을 맡길 수 있는지, 얼마가 드는지, 방문 예약은 어떻게 하는지 알 수 있도록 소개 페이지를 만들어 주세요. brief.md의 자료와 기존 예약 안내 링크를 사용하고, index.html을 열면 볼 수 있게 해 주세요.
```

[`docs/eval-new-page/`](eval-new-page/)로 시작합니다. 평가자는 스텁의 `/`에서 1280px·360px로 각각 페이지를 열고, 처음 눈에 들어오는 내용과 아래 질문의 답을 찾은 위치를 기록합니다. 세 항목을 각각 판정하고 모두 충족하면 사례를 통과한 것으로 기록합니다.

- **정보 위계와 읽기 순서.** 첫 화면에서 무엇을 수리하는 업체인지 파악할 수 있다. 두 폭 모두에서 의자 다리 수리가 가능한지, 평일 저녁 7시에 방문 가능한지, 수리하면 점검비를 따로 내야 하는지 확인하고 예약 안내에 도달할 수 있다. 좁은 화면에서도 가격과 적용 조건을 함께 읽을 수 있다.
- **시각 방향.** 평가자가 실제 화면의 조판·배치·그림 중 구체적인 선택을 가리키고, 그 선택이 생활 수리 업체의 성격과 방문자의 판단을 어떻게 드러내는지 설명할 수 있다. 예를 들어 수리 대상과 고장 유형을 작업 명세처럼 짝지을 수 있다. 다른 표현도 같은 기준으로 판정하며 색상·서체·구성의 개수는 채점하지 않는다.
- **자료와 예약 경로.** 서비스 범위와 방문 시간, 점검비 15,000원의 포함 조건, 기본 수리 30,000원부터·부품비 별도가 원자료와 일치한다. 가상의 업체임을 알 수 있고 근거 없는 후기·보증·가격이 없다. 예약 안내 링크를 열면 제공한 `booking.html`에 도달하며, 링크를 여는 것만으로 예약됐다고 표시하지 않는다. 두 입력 파일은 기준 커밋과 같다.

화면을 보지 못한 경우 정보 위계·시각 방향은 미관찰로 두고, 원자료 대조와 링크 확인 결과는 별도로 기록합니다.

## 확인 방법과 범위

초기 확인은 최종 파일을 대상으로 이름·설명·메타데이터와 상대 참조가 일치하는지, 불필요한 실행 의존이나 강제 중지 절차가 없는지 점검합니다. 이 확인은 실제 호스트의 발동이나 생성 품질을 검증하지 않습니다.

동작을 평가할 때는 실행자에게 해당 스킬과 요청을 주고 실제 산출물·변경 내역·도구 기록을 확인합니다. 강제로 스킬을 읽힌 실행(조건 C)은 적용 행동의 관찰이며 자동 발동 검증으로 세지 않습니다. 발동은 스킬이 제공된 환경(조건 B)에서 선택 여부를 따로 관찰합니다.

같은 자료·환경·모델에서 비교하고, 품질을 해치는 내용 누락·기능 회귀와 취향 차이를 분리합니다. 단일 결과로 일반적인 우월성을 주장하지 않습니다. 고정 자료는 의도적으로 작고 문제를 심어 둔 예시이므로 그 결과를 실제 프로젝트 전반의 품질로 확대하지 않습니다. 시간·토큰을 비교한다면 실패·수정 반복과 필요한 도구 작업까지 포함하며, 문서 바이트 수를 토큰 수로 대신하지 않습니다.

유효한 장점이 없거나 의도하지 않은 변경이 늘면 해당 지침의 범위와 구체성을 다시 검토합니다. 평가 때문에 새 운영 도구나 큰 테스트 체계를 의무로 만들지는 않습니다.
